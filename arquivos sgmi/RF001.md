## 2. Decisões tomadas

1. **Evoluir as telas de Amanda em vez de criar novas.** As rotas `interface_nova_mudanca` e `interface_editar_rascunho` já existiam, então não foi preciso mexer no `urls.py`. Os fluxos do RF-007 e do RF-008 também caem na tela de edição melhorada.
2. **Um único bloco de formulário para as duas telas.** "Nova Mudança" passou a usar o mesmo `includes/card_formulario.html` da edição. O bloco se adapta: com id (edição), mostra o identificador, o link de histórico e o botão "Enviar Mudança"; sem id (nova), mostra "Formulário de Cadastro" e só o "Salvar Rascunho".
3. **"Submissão" = botão "Enviar Mudança".** Salvar rascunho aceita campos vazios (é o "salvar e continuar depois"). A checagem de obrigatórios só acontece no envio, como faz o back.
4. **Mesmos `id`s de antes.** Todos os `id`s que o JavaScript de Amanda usa foram mantidos, para não quebrar anexos, tipo de mudança e histórico.
5. **Mesmo padrão do projeto:** JavaScript dentro do template, `fetch` com `FormData` + `X-CSRFToken`, toastr para confirmações e o componente de seleção do portal.

## 3. Problemas encontrados e como foram resolvidos

| Problema | Solução |
|---|---|
| O responsável era digitado como número de ID | Trocado pelo modal de busca do portal (`{% render_enjoyer_selector %}`), que envia o id correto e mostra o nome |
| Ao reabrir o rascunho, o responsável aparecia só como número | A tela agora preenche o id oculto **e** o nome do responsável |
| Erros apareciam só em toastr, com o nome técnico do campo (ex.: `planned_date: ...`) | Cada erro aparece embaixo do seu campo, com borda vermelha e `aria-invalid`, e há um resumo no topo do formulário. Os nomes técnicos viraram rótulos ("Data Pretendida") |
| A validação de obrigatórios usava o balão nativo do navegador, que some sozinho | Validação própria: destaca todos os vazios, mostra "Este campo é obrigatório." junto a cada um e leva o foco ao primeiro |
| As mensagens não sumiam ao corrigir | Ao digitar ou alterar um campo, o erro dele some. Quando não sobra nenhum, o resumo some também |
| Se o back devolvesse HTML (página de erro, login), o `res.json()` quebrava em silêncio | Nova função `lerResposta`, que trata qualquer resposta e mostra uma mensagem amigável |
| No "Enviar Mudança", o botão era reabilitado antes de a validação terminar | As chamadas foram encadeadas; o botão só volta quando tudo termina |
| "Nova Mudança" redirecionava sem dizer qual mudança foi criada | A confirmação mostra o identificador (ex.: `MUD-2026-00001`) antes de abrir a edição |
| O título não tinha limite na tela (o back aceita até 200) | `maxlength="200"` no campo |
| O componente do portal não tem marca de obrigatório no rótulo | Uma regra de CSS no próprio bloco adiciona o `*` vermelho. Não foi preciso mexer no componente |
| **Contraste insuficiente** (medido na verificação). Tema escuro: `*` e mensagens de erro em vermelho 2,5:1; botão "Salvar Rascunho" 1,5:1 (o AdminLTE clareia o `text-dark`); resumo de erros 3,8:1. Nos dois temas: "Enviar Mudança" 3,1:1 e "Selecionar" do responsável 2,9:1 / 4,0:1 | CSS restrito ao formulário em `card_formulario.html`: vermelho mais claro no tema escuro, texto escuro no botão amarelo, verde e azul mais escuros. Agora todos ficam acima de 4,5:1 |
| Botões "Salvar Rascunho" e "Enviar Mudança" centralizados no rodapé, em vez de à direita | O `.card-footer` do AdminLTE tem um *clearfix* (`::after`) que vira item invisível no flex. O flex foi para uma `div` interna do rodapé |
| **Bug no back:** a busca de responsáveis com o campo **vazio** dá erro 500 (`apps/portal/views.py`, linha 165: `distinct()` depois de um corte `[:15]`) | O front não faz busca vazia. Ao abrir o modal, o foco vai para a busca e aparece a orientação "Digite um nome, usuário, matrícula ou e-mail…". **Avisar o back** (seção 7) |

## 5. Como ficou o fluxo

1. Menu **Gestão de Mudanças → Nova Mudança Manual** (`/sgmi/mudancas/interface/nova/`).
2. Preencher o que quiser e clicar em **Salvar Rascunho**. O back cria a mudança (POST `/sgmi/mudancas/`), a tela confirma com o identificador e abre a edição.
3. Na edição (`/sgmi/mudancas/interface/<id>/editar/`), os dados salvos aparecem de novo, inclusive o nome do responsável.
4. **Salvar Rascunho** salva as alterações (POST `/sgmi/mudancas/<id>/rascunho/`), sempre com o formulário inteiro.
5. **Enviar Mudança**: a tela destaca os vazios; se estiver tudo preenchido, salva e chama a validação (POST `/sgmi/mudancas/<id>/validar-submissao/`). Os erros voltam para junto dos campos.

**Ambiente: rodar sempre pela `.venv` (Python 3.13).**
Com o Python 3.14 global, a tela "Nova Mudança" quebra com `AttributeError: 'super' object has no attribute 'dicts'` (`django/template/context.py`, `__copy__`). O Django 5.1 não suporta o Python 3.14, e o seletor de responsável do portal é uma *inclusion tag*, que copia o contexto do template. O código está certo; o problema é a versão do Python. Se alguém do time usar o Python 3.14, vai ter o mesmo erro (o admin do Django também usa inclusion tags).
