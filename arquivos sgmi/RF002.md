## 2. Decisões tomadas

1. **Campo "Identificador" somente leitura no formulário**, além do texto no cabeçalho que Amanda já tinha. Os critérios falam em "campo" somente leitura que "não envia alterações", então um campo dedicado deixa isso explícito para quem usa e para o leitor de tela.
2. **Sem `name` no campo.** É o jeito mais seguro de garantir que ele nunca vá ao back. O back também não aceita mudar o identificador, mas o front não depende disso.
3. **A página de detalhes foi criada já pronta**, no padrão das telas do SGMI: casca HTML + `fetch` em `GET /sgmi/mudancas/<id>/` (rota `sgmi:change_detail`, que já existe). Ela foi testada com uma rota criada **só no servidor de teste**. O `urls.py` do projeto não foi tocado.
4. **Espaço reservado nos detalhes** para o RF-003 (referência institucional) e o RF-005 (escopos afetados), que também pedem essa página.
5. **Mensagem de falha do servidor com orientação.** Para erros 5xx (como a falha na geração), a mensagem do back ganha "Tente novamente em instantes." Conflitos como "apenas rascunhos podem ser editados" ficam sem esse complemento, porque tentar de novo não resolve.
6. **Mesmo padrão do RF-001:** a função nova (`preencherIdentificador`) ficou no objeto `FormularioMudanca`, junto das outras do formulário.

## 3. Problemas encontrados e como foram resolvidos

| Problema | Solução |
|---|---|
| O identificador só aparecia como texto no cabeçalho da edição | Campo "Identificador" somente leitura no topo do formulário, preenchido pelo back |
| O cabeçalho podia mostrar "()" se o identificador viesse vazio | A nova função `preencherIdentificador` só mostra os parênteses quando há código |
| Na falha de geração, a mensagem não orientava o usuário | Erros 5xx ganham "Tente novamente em instantes."; a tela não muda e o botão volta a funcionar |
| No tema escuro, o campo somente leitura ficava **igual** aos editáveis | Cadeado (`fa-lock`) antes do campo e fundo diferente no tema escuro (no claro, o Bootstrap já deixa cinza) |
| Não existe página de detalhes nem rota para ela | Template pronto (`detalhe_mudanca.html`), testado com rota temporária só no teste. Pedido de rota ao back (seção 7) |
| Códigos longos poderiam estourar a largura no celular | `word-break` no identificador dos detalhes |
| Para testar a falha na geração, era preciso fazer o back falhar | No servidor de teste (e só nele), uma "chave" faz a geração falhar de propósito. O código do projeto não foi alterado |

## 5. Como ficou o fluxo

1. **Nova Mudança** (`/sgmi/mudancas/interface/nova/`): o campo "Identificador" aparece bloqueado e vazio, com o aviso "Gerado automaticamente ao salvar o rascunho".
2. **Salvar Rascunho**: o back gera o código; a confirmação mostra "Rascunho MUD-AAAA-NNNNN salvo com sucesso!" e abre a edição.
   - Se a geração falhar: aparece "Não foi possível cadastrar a mudança. Tente novamente em instantes.", a tela continua aberta e o botão volta a funcionar.
3. **Editar Rascunho**: o identificador aparece no campo bloqueado e no cabeçalho, e continua igual depois de salvar e reabrir.
4. **Detalhes** (`/sgmi/mudancas/interface/<id>/detalhes/`, **depois que o back criar a rota**): o identificador fica em destaque no topo; um clique seleciona o código para copiar.

### Preparar o RF-003 (Vincular a mudança a uma referência institucional)
O que o back já oferece:
- **Ver e criar:** `GET` e `POST /sgmi/mudancas/<id>/referencia-institucional/` (rota `sgmi:institutional_reference_create_detail`).
  - `GET` exige `sgmi.view_change` e devolve 404 se a mudança ainda não tiver referência.
  - `POST` exige também `sgmi.add_institutionalreference` e devolve 409 se a referência já existir.
- **Editar:** `POST /sgmi/mudancas/<id>/referencia-institucional/editar/` (rota `sgmi:institutional_reference_update`), que exige `sgmi.change_institutionalreference`.
- **Campos:**
  - `type`: `PROJETO`, `PROGRAMA` ou `ATIVIDADE` (3 opções, só uma);
  - `external_identifier`: até 100 caracteres; letras, números, `.`, `/`, `-` e `_`;
  - `reference_url`: endereço `http` ou `https`, até 500 caracteres.
- **Atenção:** esse formulário do back **recusa qualquer campo além desses três** (e do `csrfmiddlewaretoken`). A referência precisa ser enviada **num `fetch` separado**, não junto do `FormData` do formulário principal.
- **Detalhes:** a resposta de `GET /sgmi/mudancas/<id>/` já traz `institutional_reference` (`type`, `type_label`, `external_identifier`, `reference_url`). A tarefa 4 (link nos detalhes) não precisa de outra chamada. O espaço já está reservado no `detalhe_mudanca.html`.
- **Validação para envio:** o back também valida a referência e devolve os erros dentro de `institutional_reference`. Hoje a tela mostra isso como mensagem geral ("Referência institucional: …"); no RF-003, levar cada erro para junto do campo certo.

Pontos de atenção:
1. A referência só pode ser criada **depois que a mudança existe** (precisa do id). Na tela nova, a seção pode aparecer com o aviso "salve o rascunho para vincular uma referência", ou só na edição.
2. A tarefa 4 depende da mesma rota de detalhes pendente no back.
3. Mudança sem referência → o `GET` devolve 404, o que **não é erro** para o usuário (a seção só fica vazia).
